# Приёмщик задач агентов

Завершение сессии исполнителя не завершает задачу. Существующий `AgentTaskService`
сохраняет цикл «поручение → исполнение → независимая проверка → приёмка либо очередь
продолжения». `verified` означает приёмку; `succeeded` у попытки означает только
завершение исполнителя. Формат ORP и `.snarknode` не менялся.

## Контракт

В `tasks/<id>/task.json` сохраняются `spec`, `contract` (исходное поручение,
ожидаемый результат, версия и критерии), попытки и стратегии, `evidence`, `reviews`,
`reviewRuns`, бюджет, полномочия, рабочая папка, `nextStep`, `nextAttemptAt` и журнал
`effects`. События по-прежнему пишутся в `events.jsonl`. JSON заменяется атомарно.
Снимок сериализуется при постановке записи, а не позже из изменяемого объекта.

```json
{
  "goal": "Опубликовать профиль Бужи в контролируемой среде",
  "expectedResult": "Профиль опубликован и содержит имя и описание",
  "workspace": "Y:\\Процесс\\SnarkRoute\\apps\\server\\data\\agent-ops\\sandbox\\profile-demo",
  "permissions": {"fileWrite": true, "shell": "tests", "network": true},
  "checks": [
    {"type": "command", "command": "node", "args": ["--test"]},
    {"type": "http", "url": "http://127.0.0.1:4317/controlled-profile", "json": {"path": "published", "equals": true}}
  ],
  "criteria": [
    {"id": "tests", "description": "Проверки расширения прошли", "review": "machine", "checkIndexes": [0]},
    {"id": "publication", "description": "Профиль действительно опубликован", "review": "machine", "checkIndexes": [1]},
    {"id": "content", "description": "Имя и описание соответствуют поручению", "review": "model", "checkIndexes": [1]}
  ],
  "effects": [{"key": "publish", "description": "Публикация профиля", "check": {"type": "http", "url": "http://127.0.0.1:4317/controlled-profile", "json": {"path": "published", "equals": true}}}],
  "budget": {"wallMinutes": 30, "subscriptionRuns": 4, "maxTurns": 30, "providerCost": 0},
  "resourceLimits": {"vramMiB": 10000, "ramMiB": 12000, "cpuSlots": 4},
  "retry": {"maxAttempts": 4, "sameFailureLimit": 2, "delayMs": 2000, "maxDelayMs": 60000},
  "idempotencyKey": "profile-publication-1"
}
```

URL выше иллюстрирует контракт, а не устанавливает новый endpoint публикации.
Для действующего примера используйте smoke-скрипт ниже: реальный FL.ru не затрагивается.
Индексы проверок начинаются с нуля. У критерия есть `required` (по умолчанию true),
`review: machine | model | unverifiable`, `unverifiableReason`, `maxAgeMs`
(по умолчанию 5 минут). Непроверяемый пункт явно остаётся неподтверждённым.

Если передан только старый `acceptance`, пункты становятся модельными критериями;
прошедшие тесты не связываются с публикацией автоматически. Если переданы только
`checks`, формируются объективные машинные критерии этих конкретных проверок.
Без проверок результат ожидает доказательств и проверяющую модель. У существующих
сохранённых задач контракт достраивается при чтении, ключи хранения сохраняются.

Исполнителю передаётся копия задачи. Он не может менять контракт через API.
`agent_task_amend` / `POST tasks/:id/amend` разрешает поручителю уточнить требования
между этапами с обязательной причиной; старая спецификация остаётся в истории.
Полномочия, область и бюджеты через уточнение не расширяются.

## Три уровня

1. Код самостоятельно читает файлы и HTTP-ответы, проверяет JSON-поле, текст,
   содержимое, процессы и запускает команды из контракта. Симлинки не позволяют
   читать вне рабочей папки. HTTP только GET, без перенаправлений и учётных данных
   в URL, с ограничением ответа 1 МБ и таймаутом. Пустой `{}` не проходит проверку
   конкретного JSON-поля. `file_exists` не даёт содержательного доказательства.
2. Отдельный локальный проверяющий получает исходное поручение, критерии и заново
   полученные доказательства. Отчёт исполнителя передаётся как утверждения для
   проверки; его диалог и сессия не переиспользуются. Кандидат выбирается из живого
   каталога через семантическую маршрутизацию; предпочтение `AGENT_OPS_REVIEW_MODEL`
   (по умолчанию подсказка `qwen`), без привязки архитектуры к весам.
3. Неоднозначность, сложный творческий результат, невалидный ответ проверяющего,
   провал контрольных примеров или повтор без прогресса вызывают сильную модель.
   Используются те же адаптеры каталога и `rankExecutors`, жёсткие фильтры прав,
   качества, контекста и лимитов. Можно явно задать `review.forceStrong`.

Чисто объективные явно заданные машинные критерии могут приниматься первым уровнем.
Модель не может отменить провал машинной проверки. Подтверждение модельного критерия
требует ссылок на независимые содержательные доказательства той же попытки, версии
контракта и допустимого возраста. Неизвестные id, пропущенные критерии, `{}` и
невалидный JSON отвергаются. Файлы, сайты и отчёты помещаются в блок данных; их текст
не может менять полномочия или критерии. Проверяющий запускается без записи,
shell, сети, токена исполнителя и делегирования.

Локальная модель сначала проходит четыре контрольных примера: готовый профиль,
только заявление и тесты, внедрённая инструкция о приёмке, опубликованный профиль
с пустыми полями. Реальные ответы и ошибки сохраняются в `acceptor-calibration.json`.
Частичные результаты сохраняются после каждого примера и продолжаются с места
остановки. Локальный этап держит одну аренду, проверяя приоритет владельца перед
каждой генерацией; уже загруженные веса не резервируются заново. Завершённый провал
калибровки проверяется до новой аренды и не запускает повторный цикл.
Наличие модели в каталоге не означает пригодности. При провале её оценка не закрывает
задачи: используется сильная модель либо ожидание. Результат калибровки виден через
`GET /api/agent-ops/acceptor`.

Все вызовы моделей проходят обычный `ai.text`, диспетчер ресурсов и квоты.
Режим владельца и RAM/VRAM резерв не обходятся. По умолчанию сильная модель не
запускается при неизвестном остатке подписочного лимита. Явное
`review.allowUnknownSubscriptionQuota:true` разрешает ограниченную попытку с честным
неизвестным остатком, не объявляет его свободным. Платные API не используются.

## Решения и продолжение

`reviews` хранит `accept`, `continue`, `change_approach`, `wait_resource`, `blocked`,
`owner_action`, критерии, доказательства, подпись ошибки, отпечаток наблюдаемого
результата, стратегию, следующую работу и фактическую проверяющую модель.

Провал исполнимого критерия переводит ту же задачу в `queued` с конкретным
продолжением в промпте новой попытки. Возобновляется настоящая очередь, а не только
показывается сообщение. Повтор той же ошибки и результата требует новой стратегии
или другого разрешённого исполнителя. После `maxAttempts` задача `blocked`,
а не выполнена. Время и подписочные проверки входят в бюджет цепочки; GPU/RAM
ограничиваются общим диспетчером и `resourceLimits` контракта.

Квота, временный сбой сети, авторизация, неисправность процесса, таймаут, отсутствие
модели и отмена различаются. Ожидание проверяющего сохраняет `awaiting_verification`
и не перезапускает исполнителя. Повторы имеют экспоненциальную задержку с потолком.
`paused` сохраняется после перезапуска; текущий исполнитель заканчивает этап,
следующий не выдаётся. Отмена прекращает новые запуски. `mark_verified` остаётся
исключительным явным подтверждением владельца, с отдельной записью решения.

## Внешние эффекты и восстановление

До отправки, публикации или другого внешнего действия исполнитель вызывает
`agent_task_effect {taskId,key,action:"begin"}` (или `POST tasks/:id/effects/:key`).
Только `execute:true`, возвращённый **после записи на диск**, разрешает действие.
Повторная резервация возвращает false. После действия вызывается `reconcile`:
Приёмщик сам выполняет разрешённую проверку из контракта.

`started`/`unknown` не повторяются вслепую. После сбоя сначала читается результат;
если он подтверждён, действие становится `confirmed`. Если исход не установлен,
задача `unknown_outcome`; нужна независимая сверка. Только владелец с основанием
может отметить `not_performed` и разрешить новую резервацию. Сеть без объявленного
журнала запрещает автоматический повтор после неизвестного исхода.

Существующие блокировки удерживают рабочую папку во время исполнения и проверки.
После перезапуска сверяется PID исполнителя, затем свежие критерии и журнал.
Живой исполнитель либо проверяющий не запускается второй раз. Зависшая проверка
восстанавливается планировщиком. Старые доказательства сохраняются в истории, но
не становятся доказательствами новой попытки.

Граница доверия локального HTTP API прежняя: loopback без токена считается
владельцем. Произвольный сторонний агент с доступом к filesystem/loopback может
нарушить протокол журнала; глобальная exactly-once гарантия для произвольного
внешнего сайта без его идемпотентности/чтения результата невозможна. В неизвестном
исходе система сохраняет задачу и останавливает повтор. Новые интеграции обязаны
использовать журнал и точную независимую проверку результата.

## Доступ и проверка

MCP: `agent_acceptor_inspect`, `agent_acceptor_status`, `agent_delegate_verify`, `agent_delegate_pause`,
`agent_delegate_resume`, `agent_delegate_cancel`, `agent_task_effect`, `agent_task_amend`.
Они объявлены в каталоге `tools:acceptor`, instructions MCP и инструкции дочернего
агента. HTTP: существующие `tasks/:id`, `/result`, `/verify`, плюс `/pause`,
`/resume`, `/amend`, `/effects/:key`, `GET /acceptor`. `POST /acceptor/inspect` принимает
уже полученный результат на независимую проверку без лишнего запуска исполнителя;
неподтверждённый результат может вернуться в разрешённую очередь продолжения.

Мастерская → «Агенты»: критерии, доказательства с источником и временем,
решения, исполнитель, следующий шаг, число попыток, бюджет, пауза/возобновление/отмена.
Общая верхняя панель статусов сохранена.

Диспетчер открывается отдельной плашкой во вкладке «Агенты» (`/agent-ops`).
Постоянная Бужа (`/buzha`) использует тот же сервис и Приёмщик; отдельной системы
проверки для неё нет. `tool` заново читает разрешённый инструмент; `tool_used`
сверяет серверные квитанции вызовов текущей попытки, `tool_observations` заново
получает данные из прочитанных источников для смысловой проверки. `tool_scope`
проверяет весь журнал инструментов, `acceptor_cycle` — настоящее отклонение и
последовавший запуск. Это доказательства кода, а не утверждения исполнителя.
Бюджет подписочных шагов считает реальные модельные вызовы; его исчерпание
блокирует задачу и не записывается как исчерпание квоты провайдера.

Проверки: `vitest run src/agent-ops`; сборки сервера и launcher.
Сквозная контролируемая демонстрация:
`tsx apps/server/scripts/agent-acceptor-smoke.ts`.
Она выполняет реальные HTTP handlers, очередь и чтение независимого результата,
намеренно неполного в первой попытке. Исполнитель в ней управляемый тестовый,
его подмена явно отмечается в отчёте. Файлы и история сохраняются в data.
`agent-acceptor-live.ts` повторяет неполную и исправленную попытки с реальным Codex CLI
на работающем сервере. `agent-acceptor-qualify.ts` отправляет существующий результат
на модельную оценку и сохраняет контрольные примеры либо точную причину ожидания.
